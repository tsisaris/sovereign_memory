## Bounded Owner rebuild operation

The existing `sovereign-memory` command now accepts `--rebuild-tier` (`relational` or `personalization`), `--rebuild-id`, and a positive `--rebuild-limit`, alongside the deployment configuration file. This maintenance mode acquires the normal Owner lock/socket, builds only the selected configured tier, runs the bounded rebuild, prints its durable request status and releases its resources. A running Owner must release its ownership first; the maintenance command never removes another live service's socket. The trusted Python equivalent is `OwnerService.rebuild_projection(tier, request_id, max_items)`; it is deliberately unavailable to ordinary socket clients.

Before replacing a projection, the Owner checks the item bound, verifies the original payload hashes and checks that every affected vector has recoverable Owner provenance. Unmanaged memories, orphaned Mem0 entity links, ambiguous Cognee chunks and excessive rows refuse the reset. The reset and receipt transition commit together on the Owner handle. Original events, payloads, removal records, Mem0 history and unrelated tiers are preserved. The old tier receipts are retained in `memory_rebuild_receipts`; current receipts become pending because the old projection has actually been retired. Fixed-width vector tables are recreated for the declared dimensions. Forgotten sources are excluded and their removal events are replayed without a model.

Repeating a request id resumes it without another reset; reusing it with another tier/model identity refuses. A new id explicitly supersedes an incomplete request. Retryable processing resumes through existing owed-receipt maintenance after restart. A tier with a processing/failed rebuild refuses retrieval rather than present a partial index as complete. The CLI exits successfully only when the request is completed. Nonempty re-embedding still requires the real selected model endpoints and can truthfully remain processing or failed.

It calls only `post("/embed", body=..., requester_agent_id=...)`, never `ensure_available`, so it cannot boot an agent or download a model. Missing shared library, endpoint outage and provider errors propagate to the existing owed-receipt flow. No tokenizer or shared client is constructed while the Owner binds storage.

For relational configuration, keep `model`, `revision` and `dimensions` in `tiers.relational.embedding`, and put the shared-client settings in its `agent_embedding` table. Do not also specify `endpoint` or `api_key_env`; the shared client owns transport and authentication. For Mem0, keep the independent `revision` beside `provider` and `config`; set `config.model`, `config.embedding_dims` and `config.agent_embedding`. The configured width must equal the vector store's explicit `embedding_model_dims`.

Each `agent_embedding` table requires exactly `revision`, `capability_id`, `agent_id`, `port`, `bootstrap_config` and `requester_agent_id`. Its revision must match the tier's revision. The port and all bootstrap values come from the deployment, with no selected URL/model/width baked into the adapter. `bootstrap_config` is the existing AgentClient configuration: `host`, `request_timeout_seconds`, `health_timeout_seconds`, `boot_retry_count`, `boot_retry_interval_seconds`, `chunk_size_bytes`, `boot_entrypoint`, `boot_agent_root`, `boot_python_executable` and `sovereign_root`. Even though the shared constructor requires boot settings, this adapter never invokes boot. Configure the service owner's actual declared values rather than inventing a local endpoint.

Requests carry one selected capability and uniquely identified passages. Responses must match the configured capability/model/revision/dimension, contain exactly those passage IDs, and contain numeric finite vectors of the declared width. Text is not normalized, prefixes are not guessed, and vectors are not averaged or truncated. Both projection identities include the capability for this provider, so switching capabilities requires rebuilding even if model/revision/width match. Mem0's Owner tier also validates vectors returned by its other providers before projection or search.

This adapter implements the Owner's chunk embedding seam, not Cognee's separate token-accounted embedding gateway; it does not invent provider token counts. No reachable Agent Embedding endpoint has been verified here. Real inference, nonempty replay and four-tier acceptance remain pending actual service readiness. The separate draft that defers LiteLLM's tokenizer remains outside the published checkpoint until its checker and compatibility gaps are resolved.

## Lazy Cognee tokenizer and strict relational vectors

`LiteLLMEmbeddingEngine` no longer resolves its tokenizer while being constructed: `tokenizer` is a cached property read first inside model worker threads (token counting and the tokenizer input-limit fallback), so an unavailable tokenizer cannot block Owner startup or the event loop. The `CogneeChunkTier` embedding check now also rejects boolean, string and other non-numeric vector entries, not only wrong width and non-finite numbers.

Native operation on a disposable Owner database, relational tier configured as `agent_embedding` with `shared_agent_client` absent from this environment: the service started, a captured event was stored durably, and its relational receipt ended `retryable_failure` with the real `ModuleNotFoundError`; the other three receipts stayed `pending`. No model was called. Not yet operated: Cognee reset, nonempty model replay, in-flight/restart races and live inference. Shutdown: `OwnerService.stop` and the runtime's maintenance loop now wait for in-flight model work only for the configured `drain_timeout_seconds`, then cancel it. Cancelling a coroutine waiting on a model call is immediate, but the blocking SDK thread behind it cannot be interrupted and runs on to the shared client's own request timeout (the interpreter joins it at exit); the receipt stays `processing`, which the next start retries. Work already on the database worker is interrupted and drained by the existing connection guard, which rolls its uncommitted transaction back before the handle closes, so DuckDB is never closed under a surviving apply. This path was reasoned from the code, not operated: no slow real provider was available and no fake one was built.

Tokenizer: the provider's own usage count is used first and no tokenizer is touched when it is present; otherwise the tokenizer loads in the worker thread, and the shared utility's existing best-effort rule applies (a failure is logged and counts 0 rather than failing a request that succeeded). The tokenizer resolver is bound when the engine is built and called lazily, which keeps tests that patch it only around construction valid.
