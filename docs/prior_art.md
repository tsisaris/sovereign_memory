# Prior art: why the code runs local copies, and what each new part reuses

Written 2026-11-02 for the finish of sovereign_memory. Shawn's words that govern it: "We're not removing the software. We're removing its reliance on SQLite. All the software stays. All the SQLite is removed. Where SQLite was used, we're using DuckDB." (2026-10-10 14:49:41). Facts below marked (measured) were read this session from PyPI's own metadata or from the files in `packages/`; facts marked (plan) come from `docs/sovereign_memory_plan.md` and `docs/capability_ledger.md` and were not re-measured.

## Why four engines run from `packages/` and not from the upstream package

The rule was to install the upstream package into the declared micromamba environment with uv, one package at a time with `--no-deps`, where that keeps every capability. For each engine below it does not, so none was installed. The reason is the same four times: the local copy is the upstream code with its storage moved to DuckDB, it takes the upstream's own import name, and two packages cannot both own one import name.

| Engine | Upstream on PyPI (measured 2026-11-02) | Local copy and what it adds | Why upstream is not installed in its place |
|---|---|---|---|
| Letta | `letta` 0.34.12, Apache-2.0, Python 3.9 or newer | `packages/letta_memory_model`, import name `letta_memory_model`: Letta's memory blocks, recall, archival passages, compaction, sleep-time and dreaming, translated onto one DuckDB handle (plan) | Letta's own store is SQLAlchemy models for its server on SQLite or Postgres (plan). Installing it brings a second storage engine and SQLite, which Shawn removed. Letta's code has no DuckDB store to select. |
| Graphiti (and Zep's open part) | `graphiti-core` 0.31.2, Apache-2.0 | `packages/graphiti_duckdb`, which ships its own `graphiti_core` module plus `graphiti_duckdb/duckdb_driver.py`, the DuckDB driver, the operations files, the Zep CE store and summariser (measured: `ls packages/graphiti_duckdb/src`) | Upstream `graphiti_core` has backends for Neo4j, FalkorDB, Kuzu and Neptune and no DuckDB driver (plan). The local package is a fork of the same module name; upstream would overwrite or be shadowed by it. |
| Zep | `zep-cloud` 4.1.0 (client of the hosted cloud service) and `zep-python` 2.0.2 (client of the discontinued Zep CE server); neither declares a licence in PyPI's metadata | Zep CE's thread summariser and user store are translated into `graphiti_duckdb/zep_summarizer.py` and `zep_ce_store.py`; Zep Cloud's closed parts are listed as the "closed remainder" in the ledger | `zep-cloud` sends the user's data to a hosted service, which Law 16 (local services only) forbids. `zep-python` only talks to a server that is no longer maintained and is not a Python package. |
| Cognee | `cognee` 1.6.6, Apache-2.0 | `packages/cognee_duckdb`: Cognee 1.6.5 source with the DuckDB graph and relational adapters, and the community DuckDB vector adapter; the installed metadata says 1.6.5 and the module loads from the local copy (measured by the earlier report) | The upstream wheel defaults to SQLite for its relational store. Installing 1.6.6 over the local copy would replace the DuckDB adapters. |
| Mem0 | `mem0ai` 2.2.1, Apache-2.0 | `packages/mem0_duckdb`, import name `mem0`, with `mem0/vector_stores/duckdb.py` (517 lines, measured) and a DuckDB history store | Same import name `mem0`. Upstream's history store is `SQLiteManager` (plan). |

What would change this: if an engine's upstream adds a DuckDB storage option, its local copy can be retired to `packages/attic/` by renaming, and the upstream installed, because the capability would then be kept.
