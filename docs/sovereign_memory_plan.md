# One DuckDB service replaces four memory stores

**Executive summary, in plain words.** The right plan is to build one memory service: a single long-running program that owns one DuckDB file (DuckDB is a database that lives in one file and needs no server) and answers every agent over a local socket (a connection between programs on the same machine that never touches the network). Inside that service run the storage layers of the four original memory products, each pointed at DuckDB instead of the database it shipped with. This is not the research project the earlier report made it out to be. When the actual source code of all four products was cloned and counted on 2026-10-17, the work resolved into **a fixed number of small functions copied from templates the projects already ship**: Cognee's graph half is a copy of its own 1,052-line Turso adapter (41 methods) with the SQL retargeted, and a Cognee team-maintained DuckDB vector adapter already exists and passes its own tests ([cognee-community DuckDB adapter](https://github.com/topoteretes/cognee-community/blob/main/packages/hybrid/duckdb/cognee_community_hybrid_adapter_duckdb/duckdb_adapter.py)); Graphiti needs 106 methods, of which **83 are ordinary SQL, 3 are vector searches, 4 are keyword searches and 4 are graph walks**, modelled on its 3,169-line Kuzu backend, plus a patch to 7 upstream functions that still send raw Cypher (Neo4j's query language) around the plug-in hooks ([Graphiti operations protocols](https://github.com/getzep/graphiti/tree/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/driver/operations)); Mem0 needs 25 methods copied from a 563-line template and a 347-line history class that is already plain SQL ([Mem0 pgvector.py](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/vector_stores/pgvector.py)). No graph database engine is needed anywhere: every graph walk in both libraries is a bounded-depth traversal that DuckDB's built-in recursive SQL performs, and DuckDB 2.0 makes that recursion about 40 times faster ([DuckDB 2.0 preview](https://duckdb.org/2026/08/17/duckdb-20-highlights)). **Exactly one dependency is missing from the whole inventory**: an asynchronous SQLAlchemy dialect for DuckDB (SQLAlchemy is the Python library Cognee, EverOS and the retired Letta server use to talk to databases; "asynchronous" means it must not block the program while waiting). Nobody has published one; the synchronous one exists (`duckdb_engine` 0.17.0, MIT), Cognee's own 892-line Turso dialect shows the shape, and building it is the first release of this project ([PyPI duckdb-engine](https://pypi.org/project/duckdb-engine/)). The features the vendors moved behind paywalls are recoverable without any reverse engineering of binaries: **Mem0 1.0.11, still on PyPI under Apache-2.0 (uploaded 2026-04-06, sha256 `ddb803be…`), contains the full graph-memory and update/delete code that Mem0 deleted ten days later** ([PyPI mem0ai 1.0.11](https://pypi.org/pypi/mem0ai/1.0.11/json)); Zep's paper discloses its method section by section ([arXiv 2501.13956](https://arxiv.org/html/2501.13956v1)); and Letta's cloud-only shared memory is a git repository, reproducible with any git remote ([Letta shared memory docs](https://docs.letta.com/concepts/shared-memory/index.md)). The only genuinely opaque items are Zep's "observations" heuristics and the numeric constants inside Mem0's platform ranking. The build order below starts with the Cognee adapter (because its oracle test already exists and the vector half is done), then the dialect, then Cognee's bookkeeping tables, then Graphiti as a maintained fork (its maintainers wrote on 2026-09-21 that they are "not planning to add new backends" ([Graphiti issue #1781](https://api.github.com/repos/getzep/graphiti/issues/1781/comments))), then Mem0, then the Letta memory model, with the owner's existing `shared_memory_router` becoming the service's client and the un-adopted Anatid candidate retired to the role of worked example. This report corrects three things in the earlier survey: a maintained Cognee DuckDB adapter exists (vector only), "engineer-weeks" are replaced by counted methods and named templates, and the clean-room route is open and lawful, not closed.

## What each original offers today, and what moved

The floor is defined by four products as they were chosen, and all four have changed since. **Letta** split in two. The Python server that ran in Docker on PostgreSQL with the pgvector add-on is frozen on an `archive` branch whose maintainers write that it "is unsupported, receives no fixes or security updates, and does not represent current Letta"; its last release was **v0.16.8 on 14 May 2026** ([Letta AGENTS.md](https://raw.githubusercontent.com/letta-ai/letta/main/AGENTS.md); [Letta releases](https://github.com/letta-ai/letta/releases)). The maintained line, Letta Code (0.34.12, 12 October 2026, Apache-2.0), keeps memory as a git repository of Markdown files called MemFS, adds background consolidation renamed "dreaming", full version history and agent-owned skills, but removed memory blocks as programmable objects and the AgentFile export format, ships "no semantic or vector index by default", and states that shared memory repositories "require cloud-hosted agents" ([Letta MemFS docs](https://docs.letta.com/letta-code/memfs); [Letta changelog](https://docs.letta.com/reference/changelog/index.md)). What matters for this plan is that **the V1 server's memory model is still fully specified by its own Apache-2.0 source**: memory blocks with `label`, `value`, `limit` and `read_only`, attach/detach to many agents, the editing tools `core_memory_append`, `core_memory_replace`, `memory_insert`, `memory_replace`, `memory_rethink`, recall (every message stored, `conversation_search`), archival passages with tags, and sleep-time agents ([Letta archive constants.py](https://raw.githubusercontent.com/letta-ai/letta/archive/letta/constants.py); [Letta memory blocks docs](https://docs.letta.com/guides/agents/memory-blocks)). That server already fell back to SQLite when no PostgreSQL address was set, which means its storage code was never welded to one engine ([Letta archive settings.py](https://raw.githubusercontent.com/letta-ai/letta/archive/letta/settings.py)).

**Zep** has a discontinued self-hosted edition and a live engine. Zep Community Edition was stopped by a post dated **2 April 2025**; its code sits in a `legacy/` folder, its last tag is v1.0.2 from 28 November 2024, and it was always a thin Go program holding users, sessions and messages in PostgreSQL while forwarding all extraction to a bundled Graphiti container ([Zep blog](https://www.getzep.com/blog/announcing-a-new-direction-for-zeps-open-source-strategy/); [legacy docker-compose](https://github.com/getzep/zep/blob/main/legacy/docker-compose.ce.yaml)). **Graphiti** is healthy: Apache-2.0, **0.31.1 on 15 October 2026**, and the only program in the survey with the four-timestamp fact model built in, where every relationship carries `created_at`, `expired_at`, `valid_at` and `invalid_at` and "old facts are invalidated, not deleted" ([PyPI graphiti-core](https://pypi.org/pypi/graphiti-core/json); [Graphiti edges.py](https://github.com/getzep/graphiti/blob/main/graphiti_core/edges.py)). Its storage shelf is the problem: Neo4j Community is GPLv3, FalkorDB is SSPL, Neptune is Amazon-only, and Kuzu (MIT) was archived on 10 October 2025 after Apple agreed on 9 October to buy the company, so Graphiti marks that driver deprecated and excludes it from its default test matrix ([neo4j README](https://github.com/neo4j/neo4j); [FalkorDB LICENSE](https://github.com/FalkorDB/FalkorDB/blob/master/LICENSE.txt); [BetaKit on the Kuzu sale](https://betakit.com/apple-strikes-deal-to-acquire-canadian-database-software-startup-kuzu/); [Graphiti helpers_test.py](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/tests/helpers_test.py)). Zep Cloud keeps proprietary extras on top: observations, context-block assembly, thread and user summaries, its own extraction and reranking models, and a managed graph service called Konig ([Zep vs Graphiti](https://help.getzep.com/zep-vs-graphiti)).

**Cognee** is intact and still the best-prepared target. It is Apache-2.0, tagged **v1.6.5 on 16 October 2026** with weekly point releases, supports Python 3.10 through 3.14, runs with no cloud key using a local GLiNER extraction model and local embeddings, and ships importers from Mem0, Zep/Graphiti and Letta ([Cognee pyproject](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/pyproject.toml); [Cognee README](https://github.com/topoteretes/cognee)). Its storage has three pluggable layers, and it already proves the pattern this plan needs: two of its graph adapters run on plain SQL engines (Turso, a SQLite-dialect engine, and PostgreSQL), two of its vector adapters run on SQL engines, and its relational layer is one SQLAlchemy adapter shared by every SQL provider ([Cognee turso graph adapter](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/cognee/infrastructure/databases/graph/turso/adapter.py); [Cognee SqlAlchemyAdapter](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/cognee/infrastructure/databases/relational/sqlalchemy/SqlAlchemyAdapter.py)).

**Mem0** is maintained (2.2.1, 25 September 2026, Apache-2.0) but its free library shrank in mid-April 2026. Version 2.0.0 deleted about 4,000 lines of graph memory, made `add()` return "ADD-only events: no more UPDATE or DELETE events, memories accumulate; nothing is overwritten", and moved graph memory, decay, temporal reasoning, "Dream" consolidation, custom categories, feedback, summaries, webhooks, export and batch operations to the paid Platform ([Mem0 changelog](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/docs/changelog/sdk.mdx); [Mem0 platform-vs-oss](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/docs/platform/platform-vs-oss.mdx)). The last free version with graph memory and consolidation was **1.0.11 of 6 April 2026**, and it is still on PyPI; the implications are in the clean-room section. The per-memory history log is a hard-coded SQLite class with no provider switch, and the library phones home by default through PostHog and an hourly notices fetch from GitHub ([Mem0 storage.py](https://github.com/mem0ai/mem0/blob/0724291bd864cf807e88ee8981c8226644e8fb42/mem0/memory/storage.py); [Mem0 telemetry.py](https://github.com/mem0ai/mem0/blob/main/mem0/memory/telemetry.py)).

## The capability floor and where each piece already exists

Before the table, the terms. **Episodic memory** is the record of what happened in each conversation. **Temporal facts** carry dates: when something became true, when it stopped, when the system learned each. **Relational reasoning** connects things across documents in a **knowledge graph**, a web of named entities joined by named relationships. **Personalization** is a standing profile. **Procedural memory** is remembered know-how. **Reflection** is a background pass that re-reads and tidies memory. **Contradiction handling** marks an old fact superseded with dates instead of overwriting or ignoring it. An **embedding** or **vector** is a list of numbers a model produces from text so that similar meanings land close together; **BM25** is the standard keyword-ranking formula; **RRF** (reciprocal rank fusion) merges several ranked lists into one.

"Open" means the code is Apache-2.0 or MIT and can be adopted; "paper/docs" means the method is published well enough to rebuild from; "opaque" means neither.

Three things follow from the table. First, **every capability except two is either open code or a disclosed method**; the opaque remainder is Zep's observation-detection heuristics and the numeric constants in Mem0's platform ranking, and both have published nearest building blocks (Graphiti's label-propagation communities with summaries; Mem0's published decay bounds). Second, the superset rule is satisfied at the capability level by fewer programs than products: Mem0's old typed-triplet graph with invalid-not-deleted edges is a strict subset of Graphiti's four-timestamp model, so adopting Graphiti and routing Mem0's extracted triplets through `add_triplet` preserves that capability rather than porting a second graph engine. Third, the earlier report's reason for adding EverOS (that episodic, profile and procedural memory were not native anywhere else) disappears once the Letta V1 memory model is kept rather than dropped: persona and human blocks, recall and archival passages are exactly episodic and identity memory, and the owner's instruction is that Letta is not dropped. EverOS remains a legitimate later addition (it is Apache-2.0 with a per-backend 35-method index contract and a 20-test oracle, counted below), but it is not in the smallest set.

The Graphiti count needs one more sentence, because it is the item the earlier report got structurally wrong. Graphiti's abstract driver has only 9 methods, but `execute_query` takes a Cypher string, and the library issues raw Cypher through it at **116 call sites in 79 functions** outside the driver package ([Graphiti driver.py line 102](https://github.com/getzep/graphiti/blob/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core/driver/driver.py#L102)). Of those, 103 sit in functions that first consult a per-backend hook (the 97-method operations protocols that the v0.28.0 redesign introduced, which every shipped backend implements in full), so a DuckDB backend intercepts them by implementing the protocols. **The remaining 13 calls in 7 functions consult no hook at all**: `graphiti.py::_get_or_create_saga` (1), `graphiti.py::summarize_saga` (2), `graphiti.py::remove_episode` (1), `search/search_utils.py::get_relevant_nodes` (1), `search/search_utils.py::get_relevant_edges` (3), `search/search_utils.py::get_edge_invalidation_candidates` (3) and `utils/maintenance/edge_operations.py::filter_existing_duplicate_of_edges` (2) ([Graphiti source tree](https://github.com/getzep/graphiti/tree/d50741d1bf463cbe3859eb73914cbff1b66839e6/graphiti_core)). Two of those, `get_relevant_nodes` and `get_relevant_edges`, run on every `add_episode` for deduplication, so without the patch ingestion fails on the first episode. The patch is mechanical (route each through the same operations hooks the other 103 calls use) but it lives in a fork, because the maintainer pevans closed the PostgreSQL-backend proposal on 2026-09-21 with "We're not planning to add new backends to Graphiti at this time" ([Graphiti #1781 comments](https://api.github.com/repos/getzep/graphiti/issues/1781/comments)). Two community precedents show the fork is tractable: `uahic/graphiti-postgres` (MIT, January 2026, a Cypher-to-SQL translator approach, alpha) and crajah's PostGraph driver in PR #1777, which bypassed Cypher entirely and claimed 28 of 28 integration tests ([graphiti-postgres](https://github.com/uahic/graphiti-postgres); [Graphiti PR #1777](https://github.com/getzep/graphiti/pull/1777)). The PostGraph approach, not the translator, is the template to follow, because no Python Cypher-to-SQL translator exists and the two abandoned ones (Cytosm, Java, 2018; Microsoft's openCypherTranspiler, .NET, archived July 2024) cannot handle the variable-length paths graph walks need ([openCypherTranspiler](https://github.com/microsoft/openCypherTranspiler)).

For Cognee the count is a copy job. The Turso graph adapter's docstring states "no recursive CTEs — k-hop neighborhoods are expanded one hop per query", so its SQL is simple two-table (`graph_node`, `graph_edge`) insert/select with JSON property columns; the DuckDB version replaces `sqlite_insert` upserts with DuckDB's `INSERT … ON CONFLICT`, replaces Turso's `vector_distance_cos(vector, vector32(?))` with DuckDB's `array_cosine_distance(vector, ?::FLOAT[n])`, and may replace the one-hop loops with `WITH RECURSIVE` (optional; the loop also works) ([Cognee turso adapter](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/cognee/infrastructure/databases/graph/turso/adapter.py); [Cognee Turso vector adapter](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/cognee/infrastructure/databases/vector/turso/TursoVectorAdapter.py)). The vector half need not even be copied: the community package `cognee-community-hybrid-adapter-duckdb` already implements `has_collection`, `create_collection`, `create_data_points`, `retrieve`, `search` (plain `array_cosine_distance`), `batch_search`, `delete_data_points` and `prune` in 628 lines, with its own 8 tests and CI, and is pinned by the Cognee team to each new Cognee release ([adapter source](https://github.com/topoteretes/cognee-community/blob/main/packages/hybrid/duckdb/cognee_community_hybrid_adapter_duckdb/duckdb_adapter.py); [PyPI history](https://pypi.org/pypi/cognee-community-hybrid-adapter-duckdb/json)). Two of its choices must change: it pins `duckdb>=1.3.2,<1.5.5` only because "duckpgq community extension is not yet published for 1.5.5", and it loads duckpgq and vss without using either, so dropping both loads frees it to run on DuckDB 1.5.6 ([adapter pyproject](https://github.com/topoteretes/cognee-community/blob/main/packages/hybrid/duckdb/pyproject.toml)).

**The one missing dependency** is an asyncio SQLAlchemy dialect for DuckDB. Cognee's relational layer uses `create_async_engine` throughout with `sqlite+aiosqlite`, `postgresql+asyncpg` or Cognee's own `sqlite+cognee_turso` dialect ([Cognee create_relational_engine.py](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/cognee/infrastructure/databases/relational/create_relational_engine.py)); EverOS's SQLite store and the archived Letta server use the same async pattern. Searches of PyPI for `duckdb-async`, `sqlalchemy-duckdb-async`, `duckdb-sqlalchemy-async` and `asyncduckdb` return nothing; `aioduckdb` exists but is a 2023 asyncio bridge forked from aiosqlite (version 0.1.0, last commit October 2022), not a SQLAlchemy dialect ([PyPI aioduckdb](https://pypi.org/project/aioduckdb/)). What building it entails, from the pieces that do exist: the synchronous dialect `duckdb_engine` 0.17.0 (MIT, released 2025-03-29, last commit 2025-10-21) supplies type mapping and SQL compilation, and its README gives the three-line Alembic implementation class that makes migrations work ([duckdb_engine README](https://github.com/Mause/duckdb_engine)); DuckDB's own Python client is DB-API 2.0 with `?` placeholders and a connection that is "thread-safe but locked for the duration of each query", so the asyncio bridge is the aiosqlite pattern of running each call in a worker thread ([DuckDB Python DB-API docs](https://duckdb.org/docs/current/clients/python/dbapi)); and Cognee's Turso dialect package, **892 lines in 7 files** (dialect 110, compiler 298, transactions 237) wrapping a vendor-supplied asyncio dialect, is the template for the shape and size of the wrapper ([Cognee turso dialect](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/cognee/infrastructure/databases/turso/dialect.py)). Whether `duckdb_engine` 0.17.0 loads against DuckDB 1.5.6 is not stated anywhere and is the first measurement on the laptop. This dialect gates only Cognee's relational and cache layers, EverOS's SQLite store and the Letta ORM; Graphiti, Mem0, Cognee graph and Cognee vector use the DuckDB client directly and are not blocked by it.

## Graph queries stay in plain SQL, and why the alternatives lose

Four ways exist to ask graph questions of data that lives in DuckDB tables, and the plan uses the first. **Plain recursive SQL** (`WITH RECURSIVE`) is DuckDB's documented route for graph traversal: bounded-depth walks with explicit cycle detection through a path list, shortest paths with a window-flag pattern, and connected components through `USING KEY` clauses, all on any DuckDB version with no extension ([DuckDB WITH clause docs](https://duckdb.org/docs/current/sql/query_syntax/with.html)). It is enough because the counted traversal needs are small: Graphiti's four traversal methods are two bounded breadth-first searches, one shortest-path distance with a depth cap, and label-propagation clustering that Graphiti's own Python already drives one hop per round; Cognee's five are k-hop neighbourhoods, bounded neighbourhood iteration, node-set subgraphs, connections, and optional connected-component metrics that the Turso adapter already computes in Python ([database_swap_effort_counted.md classification](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/cognee/infrastructure/databases/graph/turso/adapter.py)). DuckDB 2.0 rewrote the recursive engine: a one-million-edge reachability benchmark fell from **4.90 seconds on 1.5.4 to 0.12 seconds on the 2.0 preview** ([DuckDB 2.0 preview](https://duckdb.org/2026/08/17/duckdb-20-highlights)). One deprecation shapes how the SQL is written: 1.5.0 is the last release accepting recursive `UNION` without a compatibility flag, 2.0 disables it by default and 2.1 removes the flag, so new traversal queries are written with `USING KEY` from the start.

**DuckPGQ** adds SQL/PGQ, the graph pattern-matching syntax in the SQL:2023 standard, directly over existing tables with `CREATE PROPERTY GRAPH`, `GRAPH_TABLE … MATCH`, variable-length and `ANY SHORTEST` paths, PageRank and connected components, all MIT and zero-copy ([DuckDB graph queries guide](https://duckdb.org/docs/current/guides/sql_features/graph_queries.html)). It loses on three facts. DuckDB's own documentation says it "is not available in DuckDB 1.5.x" and recommends 1.4.4; its README says "DuckPGQ is a research project and a work in progress"; and it has one maintainer, no GitHub releases, and is rebuilt per DuckDB release by the community-extension pipeline rather than on its own schedule ([duckpgq community manifest](https://raw.githubusercontent.com/duckdb/community-extensions/main/extensions/duckpgq/description.yml)). Pinning the whole memory system to DuckDB 1.4.4 to keep it would forgo the 2.0 recursion speed-up, the `NEAREST` vector joins and the stable extension interface that are the reasons to be on DuckDB at all. The plan treats DuckPGQ as an optional analytics add-on to revisit after 2.0, never as a dependency of a storage method.

**LadybugDB**, the MIT continuation of Kuzu (v0.21.2, 1 October 2026), can `ATTACH` a DuckDB file, scan its tables inside Cypher with `LOAD FROM alias.table`, and `COPY` them into its own graph tables; it cannot write back to DuckDB and its storage is a separate columnar format, never a DuckDB file ([Ladybug DuckDB extension docs](https://docs.ladybugdb.com/extensions/attach/duckdb/); [Ladybug README](https://github.com/LadybugDB/ladybug)). That makes it a one-way bridge: two engines, two files, an explicit refresh step, and the graph stored outside DuckDB, which breaks rule (b). Its scanner also links a `libduckdb` shipped by Ladybug's extension server and is built against whatever DuckDB release is current at its CI time, so a file written by a newer DuckDB may not open until Ladybug rebuilds ([Ladybug CI workflow](https://raw.githubusercontent.com/LadybugDB/ladybug/master/.github/workflows/ci-workflow.yml)). The earlier report's suggestion of running Graphiti on LadybugDB is therefore withdrawn; it would have kept Graphiti's graph outside DuckDB.

**GFQL** (PyGraphistry, BSD-3-Clause, 0.60.0 on 9 October 2026) runs Cypher text in-process over pandas, Polars or GPU dataframes and accepts Arrow tables, so `duckdb.sql(...).arrow()` feeds it with no copy on the Arrow side; but the graph then lives in RAM inside the Python process, not in DuckDB, and results return to DuckDB only if written back ([GFQL overview](https://pygraphistry.readthedocs.io/en/latest/gfql/overview.html)). It is a fine analytics side-car for one-off questions ("which entities bridge these two agents' knowledge") and is permitted later, but it is not a storage path. `grand-cypher` (Apache-2.0) is partial Cypher with no `OPTIONAL MATCH` and no mutations, and PuppyGraph, the one product that runs Cypher over a DuckDB file in place, is closed-source ([PyPI grand-cypher](https://pypi.org/project/grand-cypher); [PuppyGraph pricing](https://www.puppygraph.com/pricing)).

## DuckDB's four caveats decide the service shape

**Vectors.** DuckDB's `vss` extension builds an HNSW index (a fast approximate nearest-neighbour structure) but the extension is "experimental"; the index works only in memory unless `hnsw_enable_experimental_persistence` is set, "WAL recovery is not yet properly implemented for custom indexes", an unclean shutdown can cause "data loss or corruption of the index", the whole index is re-serialised at every checkpoint, it must fit in RAM outside DuckDB's memory limit, and the documentation says "we still recommend that you do not use this feature in production environments" ([DuckDB vss docs](https://duckdb.org/docs/current/core_extensions/vss.html)). So the plan does what every mature DuckDB vector store and Cognee's own Turso adapter already do: **brute-force `array_cosine_distance … ORDER BY … LIMIT k` scans over a `FLOAT[n]` column**, with no index, no flag and no corruption path. Anatid refuses an exact scan above 100,000 rows per tenant unless told to allow it, which is a sensible guardrail to copy; at that scale the measured option is to rebuild an in-memory HNSW index from the stored column at service start and treat it as a disposable cache ([PyPI anatid](https://pypi.org/project/anatid/)). DuckDB 2.0's `NEAREST` joins are the eventual native answer.

**Full text.** The `fts` extension builds a BM25 index with `PRAGMA create_fts_index`, queried through a generated `match_bm25` macro, but "the FTS index will not update automatically when the input table changes" and must be recreated ([DuckDB FTS docs](https://duckdb.org/docs/current/core_extensions/full_text_search.html)). A memory system writes constantly, so the service tracks inserts, edits, deletions and permission changes and publishes rebuilt FTS generations atomically. Every returned identifier is checked against current authorized data and the current query predicate; an old index hit for text removed by an edit must not survive merely because its source still exists. Between generations, a disclosed freshness supplement may search changed records, but it is not presented as equivalent BM25 ranking; scanning only newly inserted rows is insufficient. Acceptance includes an edited old record, a deleted record and a permission change before and after a rebuild. Mem0's interface allows `keyword_search` to return `None` when unsupported; Graphiti's and EverOS's do not, so for them the rebuild is mandatory.

**One writer.** "One process can both read and write to the database" or "multiple processes can read, but no processes can write", never both, enforced by file locks; inside the writer, many threads are fine because appends never conflict under DuckDB's multi-version concurrency control ([DuckDB concurrency docs](https://duckdb.org/docs/current/connect/concurrency.html)). This is the single fact that fixes the architecture: **one owner service holds the file read-write and every agent reaches memory through it**, never by opening the file. The service speaks the memory API (the owner's existing `memory_event` contract) over a Unix socket, which is the pattern Anatid already uses for its `anatid-server` profile and the pattern the Letta App Server uses on loopback ([PyPI anatid](https://pypi.org/project/anatid/)). Inside the service the four engines run in one Python process. Each concurrent transaction owns a separate DuckDB connection; all statements and transaction control for that transaction use its same handle. A native DuckDB cursor creates a separate connection and must not be mistaken for a cursor inside the parent transaction. Two consequences follow. Cognee's LanceDB adapter spawns worker subprocesses; the DuckDB adapter must not, and the dataset-queue setting that "caps concurrent embedded engines" is set to keep everything in-process ([Cognee create_vector_engine.py](https://github.com/topoteretes/cognee/blob/37f788bd287750e10d7610173e5332b3843f6ebd/cognee/infrastructure/databases/vector/create_vector_engine.py)). And whether a second process can attach the file read-only while the service holds it for writing is not documented; the file-lock rule suggests it cannot, and it is measured on the laptop before any outside tool is pointed at the file. DuckDB's official multi-process answer, the Quack protocol (`CALL quack_serve(...)`, HTTP, default port 9494), is "in a beta state" since 1.5.3 with "the protocol, the function names, and implementation details all subject to change" until 2.0; it becomes an option for remote readers once 2.0 ships, and the MIT `httpserver` community extension or Arrow Flight are alternatives, but none is needed for the local-socket design ([Quack extension docs](https://duckdb.org/docs/current/core_extensions/quack.html)).

**Time travel.** Plain DuckDB has none; `SELECT … AT (VERSION => 3)` is a DuckLake feature that needs a `ducklake:` attachment with a separate catalog database, which may itself be a DuckDB file, and the DuckLake 1.0 specification was published in April 2026 as "intended for production use" ([DuckLake time travel](https://ducklake.select/docs/stable/duckdb/usage/time_travel); [DuckDB concurrency docs](https://duckdb.org/docs/current/connect/concurrency.html)). The facts themselves do not need it, because Graphiti's four timestamps already answer "what was true at time T"; DuckLake answers the different question "what did the whole memory look like at time T", and is an optional later layer on the same file. DuckDB 1.5.6 (PyPI, 28 September 2026) is the version to build on; 2.0 is a developer preview with daily builds and its storage format changes, so the build targets 1.5.x and re-measures at 2.0 ([PyPI duckdb](https://pypi.org/pypi/duckdb/json)).

## The clean-room route is open, lawful and mostly unnecessary

**What REA is.** REA, "Reverse Engineer Anything" (`morluto/rea`, MIT, blog post live 10 October 2026), is an MCP server plus agent skills that let a coding agent drive existing reverse-engineering tools (Ghidra, IDA, Hopper, Rizin, JADX, mitmdump, TShark and others) against native binaries, Electron apps, .NET assemblies, Android packages, websites via Chrome and saved network captures ([morluto/rea](https://github.com/morluto/rea)). Its star count was reported as 110k, 145k and 302k within five days, so treat all as approximate, and the repository warns that look-alike forks exist. For this project its relevance is narrow: Zep Cloud, Mem0 Platform and Letta Cloud ship no binary, so REA's decompilation strengths do not apply; only its HAR network-capture path does, and that merely records request and response pairs the vendors' own Apache-2.0 SDKs and docs already describe. REA's own disclaimer positions it for "interoperability, software preservation, and analysis of software you own or are authorized to examine".

**What artefacts exist per target.** For Mem0, the decisive artefact is the **1.0.11 source tarball**: PyPI `mem0ai` 1.0.11, `License-Expression: Apache-2.0`, uploaded **2026-04-06T11:31:43**, sha256 `ddb803bedc22bd514606d262407782e88df929f6991b59f6972fb8a25cc06001`, downloaded and inspected on 2026-10-17; it contains `LICENSE` (Apache 2.0), `mem0/memory/graph_memory.py`, `kuzu_memory.py`, `memgraph_memory.py`, `apache_age_memory.py`, `mem0/graphs/`, the ADD/UPDATE/DELETE/NONE update prompt at `mem0/configs/prompts.py` line 443, and the consolidation branches in `mem0/memory/main.py` lines 591–660 ([PyPI mem0ai 1.0.11](https://pypi.org/pypi/mem0ai/1.0.11/json)). Mem0's paper (arXiv 2504.19413) discloses the extraction window, the top-s retrieval and the LLM-decided ADD/UPDATE/DELETE/NOOP step, and the graph design with invalid-not-deleted edges ([Mem0 paper](https://arxiv.org/html/2504.19413v1)). For Zep, the paper (arXiv 2501.13956) discloses the three subgraph tiers, the bi-temporal model, invalidation by setting `t_invalid` to the invalidating edge's `t_valid`, extraction with the last four messages, label-propagation communities, the five rerankers and the FACTS/ENTITIES context format, with prompts in its appendix; the docs disclose the context-block inputs and template language and the observation API shape ([Zep paper](https://arxiv.org/html/2501.13956v1); [Zep retrieving-memory docs](https://help.getzep.com/retrieving-memory)). For Letta, shared memory repositories are documented as ordinary git: "Each shared memory repository is a Git repository hosted in Letta Cloud", cloned beside MemFS, synced with commit, push, pull and `letta shared-memory sync` ([Letta shared memory docs](https://docs.letta.com/concepts/shared-memory/index.md)); the MemGPT paper is CC BY 4.0 ([arXiv 2310.08560](https://arxiv.org/abs/2310.08560)).

**The legal shape in plain words.** In the United States, copying and taking apart a program to reach its unprotected ideas and build a compatible or competing product has been fair use since *Sega v. Accolade* (1992) and *Sony v. Connectix* (2000), and *Google v. Oracle* (2021) held that reimplementing about 11,500 lines of API declaring code for a new platform was fair use as a matter of law, while expressly leaving open whether such code is copyrightable at all ([Google v. Oracle, Cornell LII](https://www.law.cornell.edu/supremecourt/text/18-956); [Sega summary](https://en.wikipedia.org/wiki/Sega_Enterprises_Ltd._v._Accolade,_Inc.); [Connectix summary](https://en.wikipedia.org/wiki/Sony_Computer_Entertainment,_Inc._v._Connectix_Corp.)). In the European Union, Directive 2009/24/EC Article 5(3) entitles any lawful user "to observe, study or test the functioning of the program in order to determine the ideas and principles which underlie any element", Article 6 permits decompilation for interoperability under conditions, and Article 8 makes "any contractual provisions contrary to Article 6 or to the exceptions provided for in Article 5(2) and (3)" null and void ([Directive 2009/24/EC](https://eur-lex.europa.eu/legal-content/EN/TXT/HTML/?uri=CELEX:32009L0024)). What is contested or fact-dependent: whether API declaring code is copyrightable (left open, with a dissent); whether terms-of-service clauses forbidding reverse engineering or benchmarking are enforceable as contracts in the US (the *Bowers v. Baystate* line is cited from training and was not re-verified; EU Article 8 answers differently); and the Article 6(2)(c) limit against producing something "substantially similar in its expression". The decisive practical point is that **this plan contains no decompilation step at all**: every piece is Apache-2.0 code to vendor, a published method to implement, or an observation of a service one is entitled to use. The two real exposures are breaching a vendor's terms of service while holding an account (the terms of Zep Cloud, Mem0 Platform and Letta Cloud were not read; reading them is a step below), and copying expressive text such as prompts and template wording verbatim, which clean-room hygiene avoids by re-deriving behaviour and keeping observers and writers separate. The Sega and Connectix holdings were read through secondary summaries because the opinion hosts were blocked; this is a factual summary, not legal advice.

**Feature by feature.** Of the proprietary features, those **(a) already open elsewhere** are Zep's bi-temporal facts, invalidation, entity resolution, communities, hybrid retrieval and rerankers (all in Graphiti), Mem0's old graph memory and its ADD/UPDATE/DELETE consolidation (in 1.0.11), and Letta's shared memory blocks (documented V1 API, Apache-2.0 code). Those **(b) rebuildable from papers, docs or observation** are Zep's context block (paper §3 and the docs template; only the per-request selection policy is undisclosed), entity summaries (method stated in docs), thread and user summaries (thinly documented; the Mem0 paper's asynchronous summary refresh is the same pattern), Mem0's new co-occurrence graph (simpler than the old one), decay (bounds published), temporal reasoning (described as ranking boosts anchored by `reference_date`), Dream (six-step pass published as a skill), feedback, custom categories, summaries and the plumbing of webhooks, export and batch operations, and Letta's shared memory repositories (plain git). Those **(c) genuinely opaque** are Zep's observation-detection method (behaviour, API, steering and retirement rules are documented; the heuristics and model are not; the closest published building block is label-propagation communities with map-reduce summaries) and the exact constants in Mem0's platform ranking (decay time constant, graph, temporal and feedback boost weights). Zep's "fact rating" could not be located in current documentation and remains unclassified ([Zep observations docs](https://help.getzep.com/observations); [Mem0 platform changelog](https://docs.mem0.ai/changelog/platform.md)).

The earlier report at `/home/claude/reports/Shared memory system software survey.md` concluded "do not put DuckDB underneath" and recommended Cognee plus EverOS plus Graphiti-on-LadybugDB with DuckDB as a read-only mirror. ## Shared owner-service contract and acceptance order

This contract refines integration order without removing any capability-table row or any of the seven deliverables. Repair and prove the database foundation first. Then establish the smallest real write/read through the owner service and one real memory adapter, before multiplying ports; extend the same operation through all four tiers. Step 7 retains its scheduling, consolidation and remaining-capability work. Driver success alone proves none of those memory capabilities.

The field-level event contract remains the existing `memory_event_schema.json` owned by Sovereign under SA_28–SA_30. The service accepts its version 2 envelope and exact legacy version 1 input. Source event identity, actor, parent/causation links, source revision and content-addressed payload provenance survive projection into each engine. Repeated utterances remain distinct events even when their payload hashes match. Reusing an event identity with different content is refused. Legacy conversion preserves its identity and source without inventing successful processing.

Capture commits the source event, verified payload reference and four pending receipts before acknowledging durable capture. Capture acknowledgment is distinct from completion. Each receipt is bound to the same event and identifies its processor, processor version, projection version and actual attempt. Only actual successful processing produces `processed` or `processed_no_new_fact`. Unknown, queued, processing and failure states are never counted as completed. Each projection change and its own successful receipt commit together on the same connection in a short transaction; writes through a third-party adapter on another connection do not satisfy that atomicity. This is per-tier atomicity, not a distributed transaction across four engines. Model and feature work occur outside that transaction. Cross-tier completion is explicitly partial, with the unfinished tiers retained as durable work.

One process owns the DuckDB file. Concurrent requests use independently owned transactions; statements, commit, rollback and cancellation cleanup remain on the owning handle. Disconnect or cancellation cannot return a still-running or uncertain transaction to the pool. After a crash, recovery reconciles interrupted attempts and resumes unfinished deliveries idempotently by event, processor and version. Replaying a completed attempt creates no duplicate projection. Unavailable Consensus/DSPy or Embedding leaves named pending work, with bounded child enrichment that never waits for its own future output.

The standalone suite retains Cognee users, roles, tenants, dataset permissions and dataset isolation, together with the scoping capabilities of the other engines. The Sovereign deployment profile follows its universal shared-pool requirement through the router; actor identity is provenance and does not silently become a per-agent isolation rule. Each request has an explicit identity and visibility context. The same context constrains every tier, vector/keyword retrieval, cached result, graph traversal, export and importer. No fallback grants broader access. Acceptance exercises both permitted and refused operations through the public service.

Corrections retain their source and supersession lineage, including the four temporal timestamps where applicable. Forget/deletion and expiry become durable changes propagated to every affected projection, index and cache; completed deletion is acknowledged only after the required effects are observed. Search never returns a deleted, expired or unauthorized source while a stale index is being rebuilt. Audit provenance follows the declared retention policy and is not silently erased or exposed as searchable content. Retry of a correction or deletion is idempotent. Whole-memory snapshots, if enabled, obey the same visibility and retention contract.

The preserved `sovereign_pm_integration_20261009` candidate supplies reference logic for event receipts, retries, provenance and owner boundaries; adoption requires review of its exact code and behavior. It is not merged wholesale. Updating the live shared router or replacing a live Sovereign service requires separate operator authorization. The present live schema and router must be checked together: schema support alone does not prove the router can handle a version 2 event.

Acceptance records the exact revision, runtime and actual operations. Required proofs include a committed write surviving restart, a rolled-back write remaining absent, independent concurrent transactions, an interrupted attempt replayed without duplicate effects, four honest receipts, a cross-tier partial failure and recovery, permission refusals, correction/deletion freshness and retained source provenance. The local-model quality measurement, complete migrations, runtime SQLite absence and observed telemetry absence remain separate obligations. A database filename or a grep result cannot establish those properties. Cloud timings remain cloud timings; performance thresholds require representative distinct vectors, filters, repeated queries, memory use and target-machine measurements.

The intended behavior behind every capability row remains required, including graph queries requested through Cognee search. A backend that declares `supports_cypher_queries = False` must expose the supported replacement graph operation and name the unsupported syntax explicitly; refusing that search mode cannot mark the entire row complete. Proprietary observation/ranking behavior is identified as a behavior reimplementation with its own evidence, never claimed as equivalence to undisclosed internals. The Python version required by the shared plan and the repository runtime declaration are reconciled through the existing template/environment owners before final acceptance.

The intended public path is authenticated capture → schema/provenance validation → durable event, recoverable payload and pending receipts → engine `prepare` outside a write transaction → engine `apply` on the owner's native transaction handle → projection and truthful receipt committed together. Use the existing `MemoryProcessor.prepare(event, verified_payload_bytes)` / `apply(native_tx_handle, prepared_work)` seam; do not create a second event bus, queue database or parallel receipt store. Reconstructible engine projections retain their source event and revision. Engine-specific history and temporal facts retain their own semantics; they are not extra competing sources of capture truth.

Retrieval must carry the authenticated visibility context through each engine, including dataset/group/user filters, graph traversal, cache access and exports. Revalidate current source visibility, supersession, deletion and expiry before returning an indexed hit. Preserve four temporal timestamps and correction lineage. An explicit partial result may identify failed or pending tiers; it may not turn them into empty successful searches. Shared-pool deployment does not erase standalone tenant/dataset permissions, and actor provenance is not itself a grant.

The service owns file access within one installation. Independent request transactions may use separately owned handles inside that one process; a borrowed handle stays on its owning worker and is never committed, closed or replaced by an adapter. Stage model work before acquiring the write transaction. Schema upgrades run through each existing schema owner under coordinated service startup/maintenance, with exact versions and failures recorded; engine reset must preserve unrelated schemas. Do not introduce a second migration registry or infer full downgrade support from successful upgrades.

Retention and deletion are policy inputs, not invented time limits. Apply an authorized correction, forget or expiry through durable work to every affected projection/index/cache and acknowledge completion only after those effects are observed. Preserve or erase source payloads and audit/learning artifacts according to their explicit policy and visibility; retaining provenance does not authorize exposing deleted content. Crash recovery must reconcile interrupted attempts, retry by event/processor/version and avoid duplicate effects. Whole-file replacement, silent SQLite conversion and deletion of unknown schemas are forbidden shortcuts.

Separate installations own separate DuckDB files and service processes. No supported design assumes several machines can write one shared file. Cross-installation connectivity must use a versioned public service boundary, not internal table access: preserve originating installation/source-event identity, provenance and source revision; authenticate the peer and explicitly authorize imports/queries; refuse an existing identity with different immutable content and preserve correction/conflict lineage. The current Unix socket is a local boundary; remote transport, peer trust, version negotiation, export/import policy and conflict resolution beyond immutable replay are **not implemented**. Evaluate maintained existing transport/importer interfaces when that work is scoped; do not build speculative replication now. Git sharing of Letta files does not synchronize the full memory database.

Prompt learning is a cooperating subsystem with its own implementation boundary; DSPy is not another storage engine. The user-supplied research selects SkillOpt-Sleep source `1a44050fc53aa4938a7a3927b6cca550491bfe51` as the initial candidate, not an already installed or compatible service. Start through existing Consensus `log_run` records/exports and owner-linked source references; connect memory-scoped retrieval when operational. Existing `record_review_outcome` attaches a genuine review and rejects conflicting replacement; later reversals require the record owner's supported history path. A missing review label does not erase recorded corrections/checks, and provider completion is not a success label.

Map existing task/session/attempt identity, source revision/hash, supplied prompt/context, actual model or unknown, correction/check evidence, visibility and event/outcome-known times into the upstream `SessionDigest`/`TaskRecord` input. Keep richer provenance linked through the existing owner/export manifest because upstream drops unknown task fields. Do not copy final fixes into earlier inputs or automatically assert that uninspected task files are reviewed. No verified turnkey Consensus/Jules importer exists yet. The consuming task interface must load an accepted instruction artifact for its applicable task/model scope and record its version/predecessor with the attempt; installing the learner alone does not close this path.

Use upstream checks, staging/adoption and rollback for one managed learned document; keep `evolve_memory=false` and multi-skill fan-out off. Learning runs in bounded batches through existing resource/scheduling owners, without adding inference to every foreground request or blocking normal work when unavailable. The source pin is required for compatible local endpoints; local inference readiness, the source mapper, artifact consumer and eagerly imported optional SQLite readers remain concrete unresolved integration work. No learner directly opens live memory DuckDB, duplicates the four engine adapters or creates another permanent logger/archive. DSPy/GEPA remains optional for specific prompt programs; model training and shared learning are later capabilities. Stored instructions/evaluation artifacts are not proof of improvement. This guide authorizes no arbitrary model download, training run, scheduler activation, external sharing or retention deletion.

Review each provider return against this flow and its assigned source ownership. Reject redundant stores, incompatible identity/transaction semantics, placeholder receipts and broad adapter rewrites that obscure the actual operation. After collection, publish one reconciled actual source revision. The bounded Claude audit must inspect the whole revision for conflicting designs, duplicate mechanisms and bottlenecks, then implement concrete simplifications and real capture → projection → scoped retrieval → restart flows within disjoint change ownership. Existing checks and ordinary supported operations supply evidence; no new custom tests or harnesses are authorized.

## Build order: smallest set, exact interfaces, templates and proofs

The smallest set of programs is four: **Cognee** (backbone: graph, ontology, search types, `improve`, permissions, importers, MCP), **Graphiti** (dated facts, invalidation, communities, hybrid search; the whole substance of Zep), **Mem0** (scoped fact memory with consolidation and history; current 2.2.1 plus pieces vendored from 1.0.11) and **the Letta V1 memory model** (blocks, recall, archival, with git for files). Each step below names the upstream interface, the template to copy, the oracle (the existing upstream test suite that gives a pass or fail without anyone writing new tests), and the measurement that proves the step. Steps 1 and 4 are independent and may run in parallel; everything else is in dependency order. All code lands in one Python environment whose interpreter satisfies every project at once (Cognee 3.10–3.14, the community adapter below 3.14, Graphiti and Mem0 3.10 and up), which puts it at 3.12 or 3.13.

**Step 0 — four measurements on the laptop before any code.** Whether `duckdb_engine` 0.17.0 imports and connects against DuckDB 1.5.6 (nobody states it). Whether a second process can open the DuckDB file read-only while the service holds it read-write (undocumented; the file-lock rule suggests no). The latency of a brute-force `array_cosine_distance` scan at the row counts the ecosystem will actually hold, which decides whether the in-memory HNSW cache is ever needed. The time to rebuild an FTS index at those sizes, which sets the rebuild schedule. Each is one DuckDB SQL statement or one import; each result is written down before Step 1.

**Step 1 — Cognee graph on DuckDB, extending the existing adapter.** Interface: `GraphDBInterface` (53 defs, 21 abstract) in `cognee/infrastructure/databases/graph/graph_db_interface.py`, registered with `use_graph_adapter("duckdb", …)` beside the existing `use_vector_adapter` call. Template: `graph/turso/adapter.py` (1,052 lines, 41 methods, two tables `graph_node` and `graph_edge` with JSON properties) for the SQL, with `graph/postgres_demo/adapter.py` (1,784 lines, 62 methods) for the methods Turso leaves to Python; `supports_cypher_queries = False` as PostgreSQL's adapter already declares, so the `CYPHER` search type is honestly refused. Changes to the community package: remove the `duckpgq` and `vss` loads and the `<1.5.5` pin, keep `array_cosine_distance` scans. Oracle: add `"duckdb"` to the `params=["ladybug","postgres","neo4j"]` fixture of `test_graph_provenance_adapter_contract.py` (20 tests), plus the package's own 8 tests and `adapter_contract_tests.yml`. Proof: the 20 contract tests pass with `GRAPH_DATABASE_PROVIDER=duckdb` and `VECTOR_DB_PROVIDER=duckdb`, run inside one process with no subprocess workers. Cognee's relational and cache layers stay on SQLite only until Step 3; this is stated as temporary, not deferred, because Step 2 is the next item.

**Step 2 — the asyncio SQLAlchemy dialect for DuckDB, released as its own package.** This is the one piece nobody has built. Existing memory from any earlier run is pulled in through Cognee's importers (`Mem0Source`, `ZepSource`/`GraphitiSource`, `LettaSource`, `COGXArchiveSource`) ([Cognee __init__.py](https://github.com/topoteretes/cognee/blob/main/cognee/__init__.py)). ## Conclusion

The question changed shape once the code was counted. "Can DuckDB sit under four memory products" turned out to be the wrong framing; the right one is "how many functions, against which templates, with which existing tests as judge", and the answer is a bounded list in which the only invention is a database dialect that follows a pattern SQLAlchemy already ships for SQLite. The products' own recent history helped more than it hurt: Cognee's move to SQL-backed Turso and PostgreSQL graph adapters, Graphiti's v0.28.0 operations redesign that put 103 of 116 queries behind hooks, and Mem0's plain-SQL history class each left a template exactly where this plan needs one. The licence rule, which eliminated every graph server, also eliminated the temptation to keep a second engine beside DuckDB, and the one-writer rule, which looked like an obstacle, dictated the one architectural decision that makes the system "continuously integrated" in the owner's sense: a single service, a single file, and cross-memory questions answered by ordinary SQL joins between what used to be four databases.

Two things remain genuinely open and should be treated as such rather than estimated. The first is whether local models are good enough for Graphiti's structured-output extraction; its README says small models "frequently emit JSON that doesn't match the requested schema", and the Apache-2.0 LongMemEval harness in Step 4 is the only honest way to find out, since no vendor has published that number. The second is the Letta step, whose counts were not taken; it is the smallest of the four in scope but the only one without a measured oracle, and it is the step where the owner's insistence that Letta not be dropped costs real maintenance of retired code. Everything else in this plan is a copy, a retarget and a test run that already exists.

The isolated project environment is declared by the `environment` prefix in `.copier-answers.yml`. `micromamba-uv.txt` owns the interpreter creation specification; root `requirements.txt` is the measured installed-distribution record under SA_93. `pyproject.toml` and `uv.lock` declare and resolve dependencies. Development and upstream-oracle dependencies in this environment do not establish that production paths avoid SQLite.
